### New controlled-Pokémon handlers

#### Close Combat

Supplied PTU source: user Defense and Special Defense are each lowered by 1 Combat Stage.

Runtime behavior:

- after a reported successful hit, Defense -1 CS and Special Defense -1 CS;
- normal Combat Stage bounds [-6,+6] are enforced;
- no target state is stored.

#### Leaf Storm

Supplied PTU source: lower the user's Special Attack by 2 Combat Stages **after damage**.

Runtime behavior:

- after a reported hit, UI asks only `Did this Move deal damage?`;
- confirmed damage -> user Special Attack -2 CS;
- no exact enemy HP/damage value is requested because the effect needs only whether damage occurred.

#### Petal Dance

Supplied PTU source: **after damage is dealt**, user becomes Enraged and Confused.

Runtime behavior:

- after a reported hit, UI asks only whether damage was actually dealt;
- confirmed damage sets `ledger.conditions.enraged=true` and `ledger.conditions.confused=true`;
- detailed cure/save automation is intentionally outside this pass.

#### Charge Beam

Supplied PTU source: after a successful hit, roll 1d20; on 7+, user gains +1 Special Attack CS.

Runtime behavior:

- on a reported hit, UI requires an additional **physical d20** result;
- 7–20 -> +1 Special Attack CS;
- 1–6 -> no increase;
- no RNG is generated by the application.

## Full-rebuild idempotency fix

During integration, the legacy physical-dice patch could leave `async async function pokemonCombatOpenMove` when the full Combat stack was rebuilt over an already-async ledger declaration.

`apply_stage_b_combat_session_fixups.py` now normalizes that declaration after all deterministic Combat layers and fails if any duplicate `async async function` remains.

This was a build-pipeline idempotency issue, not a rules/runtime design change.

## Recommended next pass

Connect source-explicit **Ability and Form action/frequency costs** to the existing shared Pokémon Combat ledger rather than maintaining a second resource system.

Suggested order:

1. expose a generic ledger API for a non-Move source with `actionCost`, `frequency`, source key and label;
2. wire only Forms/Abilities whose supplied source already has unambiguous action/frequency metadata;
3. preserve manual/GM gates where activation semantics remain incomplete or conflicting;
4. keep physical dice/manual outcome input for any Ability that needs a roll;
5. add correction/refund controls so a mistaken click does not permanently consume a Scene/Daily resource;
6. add deterministic tests for action conversion, Scene/Daily reset, source-key separation and no double-spend.
